# P0.3: Turn on the App Proxy and measure shop recognition by link kind (backend plan, revised)

## 0. Verdict

- **No widget change is needed for the proxy itself, and no migration.** PR #73 has been live since 2026-10-04. It already runs `detectViaStorefront()` → `redeemLinkCode(code,'shop')` → `probeAuth(true)` (04 §5.2–§5.3). The owner's setup is Shopify app config, not a theme upload.
  - Stage C, the widest audience, depends on one of two things: the lawyer signs off the consent popup's widget-authored benefit bullets, or a small widget task removes them (§12, Appendix A).
- **Blocking finding.** As the backend stands today, the proxy does **not** make a shop-logged-in visitor tier 3. It works only for visitors who already have a Customer-Account OAuth token, i.e. people who used the chat's „Anmelden“ before.
  - After the widget redeems the whoami `linkCode`, it asks `GET /api/auth/me` who it is.
  - `src/app/api/auth/me/route.ts → GET` (L51–57) answers `{signedIn:false}` when `getValidAccessToken(customerId)` returns nothing.
  - A shop-native login never creates a token. Only `api/auth/shopify/callback` → `saveCustomerTokens` does.
  - The widget treats that answer as definitively anonymous (04 §2.5). The visitor sees „Anmelden“ and the login popup, **not** the consent popup.
  - The same token requirement sits in `src/lib/account-guard.ts → requireSignedInCustomer` (L56–67, all `/api/account/*`, including `POST /api/account/marketing-opt-in`) and in `src/lib/customer-memory.ts → resolveSignedInMemory` (L206–211).
  - docs/CUSTOMER_ACCOUNT.md already says so: „History for a *pure shop-native* session: `/api/account/*` still require a live Customer-Account token“.
  - The claims in 04 §17 („cheapest lever“) and 04 §10.4 (row „Recognised by whoami“ → consent popup) therefore hold only for customers with a token.
- **Switching the proxy on as-is has four more effects:**
  1. *Hidden link plus false KPI.* For token-less customers, `storefront/route.ts` still mints a code. The widget redeems it, so the session gets an `app_proxy` link and `account_signin_linked {kind:'app_proxy'}` is recorded („Vom Shop erkannt“). `redeemLinkGrant` then stamps the session's conversations with the customer id, while the UI says anonymous.
  2. *Cross-customer data move (shared browser).*
     - `customer-link-grant.mjs → redeemLinkGrant` (L92) re-stamps **every** conversation of the sid with no ownership guard, and `linkSessionToCustomer` re-points the link to the new customer.
     - Scenario: A is signed in on sid S and logs out of the shop only, which the open tab does not notice (04 §5.6). B logs in to the shop and opens a new tab. whoami issues B a code for S, and the widget redeems it with no action.
     - Result: A's conversations show up in B's history and export (`account-history.ts` L88 lists `WHERE co.customer_id = …`).
  3. *Replayable sign-in.*
     - Signed App Proxy URLs never expire, because `evaluateAppProxyAuth` checks no timestamp.
     - The route is publicly reachable; the HMAC is its only guard.
     - Anyone holding one signed query string could get a `linkCode` and redeem it at `POST /api/auth/link` with `x-ms-session` = the signed sid. The chat key is public, and a non-browser client can set any Origin.
     - Every replay also refreshes `authenticated_at` (app_proxy→app_proxy takes the ELSE branch of `linkSessionToCustomer`).
  4. *Renewals look like sign-ins.*
     - On every new tab session, PR #73 calls whoami before `/api/auth/me`, even on a sid that is already signed in (04 §2.3–§2.4).
     - `redeemLinkGrant` returns the **grant** kind. So an already-signed-in customer records `account_signin_linked {kind:'app_proxy'}` once per tab session.
- **Plan.** Two backend phases with two env switches, both default off.
  - **Phase 1** (M, ship before the proxy goes on): measurement and safety.
    - A server-only `account_shop_recognised` event.
    - A code only when `/api/auth/me` will really sign the session in.
    - Mandatory timestamp freshness (replay).
    - Handover: a different shop customer ends the sid's previous sign-in.
    - An ownership guard on the conversation stamp.
    - `renewed` / `kind` on the link events, a kill switch, signature reporting, and dashboard splits plus a drift alarm.
  - **Phase 2** (M, behind maintainer decision **D-AP1** and lawyer Prüfbitte **F-36**): a fresh `app_proxy` link counts as signed in without a token. That makes every shop-logged-in opener tier 3, and they are offered the consent popup. It also adds:
    - per-customer anti-nag for the consent ask;
    - proof in the consent evidence;
    - repair of dead Customer-Account links;
    - logout ending app_proxy links.
- **Rollout:** Stage A (measure only) → Stage B (only customers with a live chat token) → Stage C (D-AP1, after F-36 and the Stage C preconditions in §7).
- **Deviation from the user's item 7.** `account_signin_linked {kind:"app_proxy"}` cannot appear in Stage A, because the flag is off and no code is issued. It is confirmed in the **Stage B token-holder test** (§8). docs/ROLLOUT_TODO.md §5.4 goes on hold until Phase 1 is deployed (§6, §7).
- **Total effort:** M–L (Phase 1 M, Phase 2 M, Appendix A widget S, ops S).

**D-AP1 reasoning:**
- The shop proof is re-established on every tab session's whoami.
- It is actively ended on a shop logout (`not_logged_in` → `unlinkAppProxySession`) and on a change of shop customer (handover, §3.6).
- It is bounded by the max age. Replays are blocked by timestamp freshness (§3.5).
- Order status stays `customer_account`-only (ANWALTSDOSSIER §16.1, F-32).

**D-AP1 rests on one unverified premise.** The draft said that a shop logout does not revoke the Customer-Account token. The backend assumes the opposite: the `src/app/api/auth/me/route.ts` revoked-token branch (L64–73) treats a 401 as „logged out of Shopify OUT-OF-BAND“, and docs/CUSTOMER_ACCOUNT.md calls the token the „liveness/logout proof“.
- Verify this on live in Stage A (§8, „Shop-logout token test“) **before** D-AP1 goes to the maintainer and the lawyer.
- If a shop logout does revoke the token, the shop proof is weaker than the token proof only by the window in which the same tab does not notice a logout. The 24 h max age bounds that in either case.

## 3. Phase 1: measurement, safe code issuing, replay and handover protection, kill switch (ship first)

### 3.1 Switches: `src/lib/platform-flags.mjs` (+ `platform-flags.test.mjs`)
- `isAppProxySigninEnabled(env = process.env)` → `parseFlag(env.APP_PROXY_SIGNIN_ENABLED)`, default **false**.
  - When false, whoami never issues a code.
  - It is also the drift kill switch: a Vercel redeploy, with no Shopify access needed.
- `appProxySigninMaxAgeHours(env)` → `parseNonNegativeInt(env.APP_PROXY_SIGNIN_MAX_AGE_HOURS, 0, 720)`, default **0** (today's rule: a token is required).
- `appProxyShopProofHours(env)` → `isAppProxySigninEnabled(env) ? appProxySigninMaxAgeHours(env) : 0`. With the kill switch off, token-less shop links stop counting too.
- `.env.example`: both variables with default and purpose, next to `SHOPIFY_APP_PROXY_SECRET`.

### 3.2 Pure rules: new `src/lib/signed-in-proof.mjs` (+ `signed-in-proof.test.mjs`)

**`shopRecognitionProof({ hasToken, shopProofHours })`** returns:
- `'shop'` if `shopProofHours > 0`;
- else `'token'` if `hasToken`;
- else `'none'`.

**`decideShopRecognition({ flagOn, shopProofHours, hasToken, liveToken, linkedShopifyCustomerId, shopifyCustomerId })`** returns `{ action: 'handover'|'no_code'|'issue', proof, hasToken, alreadySignedIn, noCode: null|'flag_off'|'no_proof'|'handover' }`. Checks run in this order:
1. A signed-in link of the sid to **another** Shopify customer → `handover`.
2. `alreadySignedIn` = the sid's signed-in link belongs to this customer.
3. `proof = shopRecognitionProof({ hasToken: liveToken, shopProofHours })`.
4. `!flagOn` → `no_code` / `flag_off`.
5. `proof === 'none'` → `no_code` / `no_proof`.
6. Otherwise → `issue`.

**`signedInProofFor({ linkKind, authenticatedAt, nowMs, shopProofHours })`** (Phase 2) returns:
- `'token'` for `customer_account`;
- `null` for `email`, `legacy` or an unknown kind;
- for `app_proxy`: `'shop'` if `shopProofHours > 0` and `authenticatedAt` is valid, at most 60 s in the future and not older than `shopProofHours`; else `'token'`.

**`signInProofNote(proof)`** (Phase 2, consent evidence) returns:
- `'token'` → „Anmeldenachweis: Kundenkonto-Anmeldung im Chat“;
- `'shop'` → „Anmeldenachweis: Shop-Login (App Proxy)“.

### 3.3 Event name: `src/lib/kpi-events.ts` and `src/lib/kpi-widget-events.mjs`
- Add `export const KPI_ACCOUNT_SHOP_RECOGNISED = "account_shop_recognised";`.
  - The spelling matches the existing diagnosis key `shop_recognised`, so the exact-literal SQL (also duplicated in `scripts/verify-live-kpis.mjs`) cannot drift.
- Meaning: on a fresh, signed whoami request, Shopify vouched for a logged-in customer.
- `data: { proof: "token"|"shop"|"none", hasToken: boolean, alreadySignedIn: boolean, codeIssued: boolean, noCode?: "flag_off"|"no_proof"|"handover"|"failed" }`, session-keyed. It never carries a customer id, name, e-mail, the code or the URL.
- Add it to `SERVER_ONLY_EVENTS`, so `POST /api/kpi` drops it (AC §5).
- The name matches none of `CTA_PATTERNS` / `CART_PATTERNS`. Extend the existing test „no new event counts as a product click or a cart click“.
- Additive fields on existing server events (AC §5, kpi-widget-events tests):
  - `account_signin_linked {kind, renewed}`. `renewed` is true when the sid already had a signed-in link to the same customer.
  - `account_signin_link_refused {reason, kind?}`. `kind` is the grant's `link_kind` when the grant row is known.

### 3.4 Token lookup: `src/lib/customer-oauth-store.ts`
`findChatTokenCustomer(shopifyCustomerId: string, sql = getSql()): Promise<{ customerId: number | null; hasToken: boolean }>`
- Null-safe and wrapped in try/catch. On error it calls `reportError(err, { route: "lib/customer-oauth-store", phase: "findChatTokenCustomer" })` and returns `{ customerId: null, hasToken: false }`.
- It is a cheap existence check, used for **measurement** (`hasToken`, recorded in every stage):

```sql
SELECT c.id AS customer_id,
       EXISTS (SELECT 1 FROM customer_oauth_tokens t
                WHERE t.customer_id = c.id
                  AND (t.refresh_expires_at IS NULL OR t.refresh_expires_at > now())) AS has_token
  FROM customers c
 WHERE c.shopify_customer_id = ${shopifyCustomerId}
 LIMIT 1
```

- **Issuing a code in Stage B uses the exact check.** The route calls `getValidAccessToken(customerId)`; `/api/auth/me` calls it moments later anyway, and rotation is persisted atomically before return. The cheap check is not enough there: a rotated or invalid refresh token, or a revoked access token, would otherwise still get a code and a „Vom Shop erkannt“ link while `/api/auth/me` says false.
- Residual risk: an access token that is revoked but not yet expired passes `getValidAccessToken`, because it is not validated against Shopify. `/api/auth/me` then hits the revoked-token branch, deletes the tokens and answers false. It is one-time per customer (§10, Stage B test).

### 3.5 Signature, freshness and diagnostics: `src/lib/shopify-app-proxy.mjs` (+ test)
- **`isFreshAppProxyTimestamp(query, nowMs, maxSkewSec = 300)`** (mandatory, O1).
  - True only for a numeric `timestamp` param within ±300 s of `nowMs`.
  - Missing or non-numeric means stale.
  - Shopify adds `timestamp` to every App Proxy request, and it is covered by the signature.
- **`appProxyFailureKind(query, secret, nowMs)`** returns:
  - `null` when the signature is valid and fresh;
  - `'unsigned'` when there is no `signature` param (a direct hit, scanner or curl; stays silent);
  - `'no_secret'` when signed but no secret is configured;
  - `'mismatch'` when the signature does not match;
  - `'stale'` when the signature is valid but the timestamp is missing or outside the window.
- `evaluateAppProxyAuth` stays unchanged, so the existing `deepEqual` tests keep passing.
- Residual risk: a replay **within** 5 minutes by someone who can read request logs (team members with Vercel access). Optional O1b: a KV `SET NX` on `sha256(signature)` with a 300 s TTL refuses a second use. It fails open like the rate limiter, so it is hardening, not a gate.

### 3.6 Route: `src/app/api/auth/storefront/route.ts → GET`
New order. DB writes on the logged-in path happen only when a code is really issued, or when a handover ends a link.

1. **Signature and freshness.** Compute `const failure = appProxyFailureKind(url.searchParams, appProxySecret(), Date.now())`.
   - For `failure ∈ {no_secret, mismatch, stale}`, call `reportError(new Error("App Proxy signature " + failure), { route: "api/auth/storefront", phase: failure })`.
   - Throttle it with a module-level timestamp per kind: at most once per 10 min per instance.
   - Never pass the URL or the query (they contain `logged_in_customer_id`, `session` and `signature`).
   - On any failure, return `{signedIn:false}`. A stale request never ends a link.
2. **`evaluateAppProxyAuth`** (unchanged). On `not_logged_in`, run `endAppProxySessionLink` (unchanged) and return false.
3. **Rate limit** (unchanged).
4. If `!auth.sessionId`, return `{signedIn:false}`: no code is possible and no event can be keyed.
5. **Reads, in parallel:**
   - `current = await currentSignedInLink(auth.sessionId)`, a null-safe TS wrapper over `resolveSignedInLink` that reports via `reportError(err, { route: "api/auth/storefront", phase: "currentLink" })`;
   - `token = await findChatTokenCustomer(auth.shopifyCustomerId)`.
6. **Token check:** `const hours = appProxyShopProofHours(); const flagOn = isAppProxySigninEnabled();`.
   - `liveToken` is exact (`getValidAccessToken(token.customerId) != null`) only when it decides a code: `flagOn && hours === 0 && token.hasToken && token.customerId != null && current?.shopifyCustomerId` is not another customer.
   - Otherwise `liveToken = token.hasToken`.
7. **Decide:** `const d = decideShopRecognition({ flagOn, shopProofHours: hours, hasToken: token.hasToken, liveToken, linkedShopifyCustomerId: current?.shopifyCustomerId ?? null, shopifyCustomerId: auth.shopifyCustomerId })`.
8. **`handover`:**
   - `await endSessionSignedInLink(auth.sessionId)`, a TS wrapper over the new `customer-link-grant.mjs → unlinkSessionSignedIn(sql, sid)` that deletes `session_id = sid AND link_kind IN ('customer_account','app_proxy')`. It removes only this sid; the previous customer's other devices stay signed in.
   - Record the event with `noCode:'handover'` and return `{signedIn:false}`.
   - The widget then probes `/api/auth/me` (the device hint is set), gets `signedIn:false` and runs `endedSignInCleanup()`: it wipes the local transcript and rotates the sid (04 §2.5, 02 §7.3). The next tab links the new person on a fresh sid. The previous person's local and server data never reach the new person.
   - This runs in **every** stage once the proxy is on. In Stage A it is the only visible change, and it is protective.
9. **`no_code`:** record the event and return `{signedIn:false}`. No Admin API call, no bind, no code. This removes the hidden link and the false KPI.
10. **`issue`:** run the existing path (Admin API → bind → mint).
    - If `linkCode == null`, record `codeIssued:false, noCode:'failed'` and return `{signedIn:false}`.
    - Otherwise record `codeIssued:true` and return the existing response.

Contract: the shape is unchanged. `signedIn:true` now always comes with a `linkCode`, and every other case is `{signedIn:false}`, which CA §3a already allows as the fail-closed answer. The widget treats `signedIn:true` with `linkCode:null` as not signed in anyway (04 §5.3).

### 3.7 Grant redeem and link events: `src/lib/customer-link-grant.mjs` (+ test), `src/lib/session-link-grants.ts`, `src/app/api/auth/link/route.ts`
- **Ownership guard on the stamp** (Gate 0):

  ```sql
  UPDATE conversations SET customer_id = ${customerId}
   WHERE session_id = ${sid} AND (customer_id IS NULL OR customer_id = ${customerId})
  ```

  - A sid's conversations never move between customers. This also applies to the chat sign-in: a conversation stamped by another customer's typed e-mail stays with that customer.
  - The fake sql in `customer-link-grant.test.mjs` must emulate the new condition (values `[customerId, sid, customerId]`).
- **`renewed` and `priorKind`.** Before the upsert, `redeemLinkGrant` reads `SELECT customer_id, link_kind FROM customer_session_links WHERE session_id = ${sid}`.
  - It returns `{ ok: true, customerId, kind, renewed, priorKind }`, where `renewed` = the prior link has a signed-in kind and belongs to the same customer.
  - The fake gets a handler for this SELECT.
- **Kind on refusals.**
  - On `session_mismatch`, the grant row is known, so return its `link_kind`.
  - On `invalid`, look it up with one PK read: `SELECT link_kind FROM customer_link_grants WHERE code_hash = …`. It returns nothing for an unknown code.
  - The result is `{ ok: false, reason, kind: string | null }`.
- **`/api/auth/link → POST`:**
  - On success: `recordKpiEvent(… KPI_ACCOUNT_SIGNIN_LINKED, data: { kind: result.kind, renewed: result.renewed })`.
  - On refusal: `{ reason, ...(kind ? { kind } : {}) }`.

### 3.8 Aggregation: `src/lib/kpi-store.ts`
All SQL is spelled out; no tagged templates are composed. Every new query excludes `session_id LIKE 'livecheck-%'`, the manual live check (§8).

Counting rules:
- An **app_proxy** link counts as a sign-in only with `renewed = false`. Renewals are counted separately.
- A **customer_account** link counts whether renewed or not, because it is always a click on „Anmelden“.
- The redeem rate and the drift alarm use **all** codes, renewals included.
- Events from before Phase 1 have no `renewed`, so `COALESCE(…,'false')` applies. Only chat sign-ins exist from that time, because the proxy was off.

**(a) `getAccountActivity`.** Add a third parallel query and these fields:
- `linkedSessions: { signin, shop, renewedOnly }`
- `shopRecognition: { recognised, recognisedNew, withToken, withCode, redeemed, refused, flagOff, noProof, handover, codeFailed, rates }`

The UI uses these session counts instead of the event count `linkedSignins`. That field stays for compatibility.

```sql
WITH s AS (
  SELECT session_id,
         min(created_at) FILTER (WHERE event = ${KPI_ACCOUNT_SHOP_RECOGNISED}) AS recognised_at,
         bool_or(event = ${KPI_ACCOUNT_SHOP_RECOGNISED}
                 AND COALESCE(data->>'alreadySignedIn', 'false') = 'false') AS recognised_new,
         bool_or(event = ${KPI_ACCOUNT_SHOP_RECOGNISED} AND data->>'hasToken' = 'true') AS has_token,
         min(created_at) FILTER (WHERE event = ${KPI_ACCOUNT_SHOP_RECOGNISED}
                                   AND data->>'codeIssued' = 'true') AS code_at,
         bool_or(event = ${KPI_ACCOUNT_SHOP_RECOGNISED} AND data->>'noCode' = 'flag_off') AS no_code_flag_off,
         bool_or(event = ${KPI_ACCOUNT_SHOP_RECOGNISED} AND data->>'noCode' = 'no_proof') AS no_code_no_proof,
         bool_or(event = ${KPI_ACCOUNT_SHOP_RECOGNISED} AND data->>'noCode' = 'handover') AS handover,
         bool_or(event = ${KPI_ACCOUNT_SHOP_RECOGNISED} AND data->>'noCode' = 'failed') AS code_failed,
         bool_or(event = ${KPI_ACCOUNT_SIGNIN_LINKED} AND data->>'kind' = 'customer_account') AS linked_signin,
         bool_or(event = ${KPI_ACCOUNT_SIGNIN_LINKED} AND data->>'kind' = 'app_proxy'
                 AND COALESCE(data->>'renewed', 'false') = 'false') AS linked_shop_new,
         bool_or(event = ${KPI_ACCOUNT_SIGNIN_LINKED} AND data->>'kind' = 'app_proxy'
                 AND data->>'renewed' = 'true') AS linked_shop_renewed,
         max(created_at) FILTER (WHERE event = ${KPI_ACCOUNT_SIGNIN_LINKED}
                                   AND data->>'kind' = 'app_proxy') AS shop_linked_at,
         max(created_at) FILTER (WHERE event = ${KPI_ACCOUNT_SIGNIN_LINK_REFUSED}
                                   AND data->>'kind' = 'app_proxy') AS shop_refused_at
    FROM kpi_events
   WHERE event IN (${KPI_ACCOUNT_SHOP_RECOGNISED}, ${KPI_ACCOUNT_SIGNIN_LINKED}, ${KPI_ACCOUNT_SIGNIN_LINK_REFUSED})
     AND session_id IS NOT NULL
     AND session_id NOT LIKE 'livecheck-%'
     AND created_at >= ${range.from}::date
     AND created_at < (${range.to}::date + 1)
   GROUP BY session_id
)
```

```sql
WITH g AS (
  SELECT session_id,
         bool_or(event = ${KPI_CONSENT_GATE_SHOWN})    AS shown,
         bool_or(event = ${KPI_CONSENT_GATE_ACCEPTED}) AS accepted,
         bool_or(event = ${KPI_CONSENT_GATE_DECLINED}) AS declined
    FROM kpi_events
   WHERE event IN (${KPI_CONSENT_GATE_SHOWN}, ${KPI_CONSENT_GATE_ACCEPTED}, ${KPI_CONSENT_GATE_DECLINED})
     AND data->>'surface' = 'signin'
     AND session_id IS NOT NULL
     AND created_at >= ${range.from}::date
     AND created_at < (${range.to}::date + 1)
   GROUP BY session_id
), w AS (
  SELECT g.*,
         EXISTS (SELECT 1 FROM kpi_events l WHERE l.session_id = g.session_id
                    AND l.event = ${KPI_ACCOUNT_SIGNIN_LINKED} AND l.data->>'kind' = 'customer_account') AS via_signin,
         EXISTS (SELECT 1 FROM kpi_events l WHERE l.session_id = g.session_id
                    AND l.event = ${KPI_ACCOUNT_SIGNIN_LINKED} AND l.data->>'kind' = 'app_proxy') AS via_shop,
         EXISTS (SELECT 1 FROM kpi_events o WHERE o.session_id = g.session_id
                    AND o.event = ${KPI_EMAIL_CAPTURE_MARKETING_OPTED_IN}
                    AND o.data->>'trigger' = 'signin_optin'
                    AND o.created_at >= ${range.from}::date
                    AND o.created_at < (${range.to}::date + 1)) AS opted_in
    FROM g
)
SELECT CASE WHEN via_signin THEN 'signin' WHEN via_shop THEN 'shop' ELSE 'unknown' END AS way,
       count(*) FILTER (WHERE shown)::int                     AS shown,
       count(*) FILTER (WHERE accepted)::int                  AS accepted,
       count(*) FILTER (WHERE declined AND NOT accepted)::int AS declined,
       count(*) FILTER (WHERE opted_in)::int                  AS opted_in
  FROM w GROUP BY 1
```

`accepted` is treated as the final state, which dedupes the widget's dismiss-after-accept (04 §10.2, §17).

## 8. Live verification

**Stage A**
- `npm run verify:widget` → „App Proxy /apps/chat/whoami antwortet JSON — signedIn=false“ and an acceptable build.

  ```sql
  SELECT created_at, data FROM kpi_events
   WHERE event = 'account_shop_recognised' AND session_id = 'livecheck-manual'
  ```

- **Shop-logout token test (D-AP1 premise):**
  1. Sign in a test customer through the chat's „Anmelden“.
  2. Log out on the shop's account page.
  3. Open a new tab and open the chat.
  - The chat still signed in means the token survives a shop logout.

- **Handover test:**
  1. Test customer A is signed in to the chat.
  2. Log out of the shop and log in as test customer B in the same browser.
  3. Open a new tab and open the chat.

One-time per customer, documented in §10.

- Redeem join (also in `verify:live` section 7):
  ```sql
  WITH r AS (
    SELECT session_id, min(created_at) AS at FROM kpi_events
     WHERE event = 'account_shop_recognised' AND data->>'codeIssued' = 'true'
       AND session_id NOT LIKE 'livecheck-%'
       AND created_at >= (('<Stage B date>'::date)::timestamp AT TIME ZONE 'Europe/Berlin')
     GROUP BY 1)
  SELECT count(*) AS mit_code,
         count(*) FILTER (WHERE EXISTS (SELECT 1 FROM kpi_events l WHERE l.session_id = r.session_id
                 AND l.event = 'account_signin_linked' AND l.data->>'kind' = 'app_proxy' AND l.created_at >= r.at)) AS eingeloest,
         count(*) FILTER (WHERE EXISTS (SELECT 1 FROM kpi_events l WHERE l.session_id = r.session_id
                 AND l.event = 'account_signin_linked' AND l.data->>'kind' = 'app_proxy'
                 AND COALESCE(l.data->>'renewed','false') = 'false' AND l.created_at >= r.at)) AS davon_neu,
         count(*) FILTER (WHERE EXISTS (SELECT 1 FROM kpi_events l WHERE l.session_id = r.session_id
                 AND l.event = 'account_signin_link_refused' AND l.data->>'kind' = 'app_proxy' AND l.created_at >= r.at)) AS abgelehnt
    FROM r;
  ```

## 9. Legal and privacy

- **Consent popup.** No new consent surface. The popup for shop-recognised visitors uses the served `surface=signin` copy: `lawyerApproved === true`, `consentTextShown` echoed verbatim, nothing pre-selected, decline as easy as accept (04 §10.2).
  - It is **not** fully compliant today. It renders widget-authored benefit bullets (`GATE_COPY.benefits`) between the served headline and `marketingLabel`, which conflicts with FP „Rules that do not change“ and CF §1 (04 §11, §18 item 17; open lawyer question 07 §8).
  - Stage C multiplies the exposure, so it depends on D-AP4 (the lawyer's sign-off or Appendix A).
  - The English signin copy is unreviewed (`CONSENT_COPY_EN_LEGAL_REVIEWED = false`), so D-AP3 is decided before Stage C.
- **KPI event.** A pseudonymous sid plus enum and boolean fields. No customer id, name, e-mail, code or URL.
  - It is server-only (dropped by `POST /api/kpi`).
  - It is caused by whoami, which runs on panel open (an interaction), so it is not an interaction-free widget event (05 §13.3).
- **Phase 1 is protective.** It removes today's latent hidden linking: without a usable proof there is no code, no link and no stamping. It also closes the cross-customer stamp, ends a previous person's sign-in on a shop handover, and blocks replays older than 5 minutes.
- **Silent recognition is new processing:** reading the shop login state when the chat opens, linking the session, attaching earlier anonymous chats of this browser to the account, and, under D-AP1, export, erase, greeting by name, personalisation and the marketing opt-in with the account e-mail. All of it happens without an action in the chat.
- **F-36 (new Prüfbitte, dossier §19.2)** asks the lawyer to cover:
  - (a) silent recognition on chat open under § 25 TDDDG, next to F-14;
  - (b) the privacy-notice text (F-05 / F-28);
  - (c) attaching earlier chats of the browser to the account;
  - (d) the D-AP1 scope, including `POST /api/account/marketing-opt-in` on the shop proof (DOI unchanged, proof recorded in `consent_events.note`) and the 24 h max age;
  - (e) `/en` (D-AP3);
  - (f) the benefit bullets (D-AP4);
  - (g) the anti-nag rule (decline per customer for 30 days, ask cap of 3 sessions in 30 days);
  - (h) the shared-browser handover.
- **The lawyer's answer is a precondition of Stage C.** Order status stays Customer-Account-only (§16.1, F-32).
- **Consent evidence.** Every Mo opt-in records which sign-in proof stood behind it (`token` or `shop`), so the Art. 7(1) audit trail can tell the two apart after Stage C.
- **Sid in the URL.** The sid already travels on the same-origin whoami URL (README invariant 6). That is unchanged, and the code binding (0073) still decides the link.

## 10. Risks and mitigations

| Risk | Mitigation |
|---|---|
| `logged_in_customer_id` is empty (new customer accounts), so the lever is 0 | Stage A shows it within a day (the manual SQL row). Fails closed. |
| Replay of a signed whoami URL (logs, leaked URL) mints a code for its sid | **Mandatory** timestamp freshness (5 min, Gate 0). Stale requests are reported (throttled) and never end or create links. Residual: a replay within 5 min by someone with log access; optional O1b KV dedupe. |
| Shared browser: the next shop customer would inherit the previous person's chat account and conversations | Ownership guard on the stamp. Handover ends the sid's signed-in link, issues no code, and the widget wipes and rotates (Gate 0). Residual: if a chat sign-in of B happens on A's sid after A's link expired, A's **local** transcript stays on screen (a widget behaviour); server data stays with A. |
| Renewals counted as sign-ins | `renewed` / `alreadySignedIn`. Sign-in KPIs count app_proxy links with `renewed=false`; renewals are shown separately. |
| Drift back to a pre-#73 widget, which shows the whoami name without redeeming | `verify:widget` alarm (exists), the dashboard Callout (redeem < 80 %), the kill-switch env. Re-check after every theme sync. |
| Wrong or missing secret looks like „nobody is logged in“ | Throttled `reportError` on `no_secret` / `mismatch` / `stale`. `unsigned` direct hits stay silent. |
| Load: every first open per tab session reaches Vercel; `not_logged_in` does a PK delete (L78, before the rate limit) | Cheap index lookups on signed requests. In Stage A, logged-in requests do two reads (link PK, token join) and **no** Admin API call. Watch Vercel invocations and Neon. |
| Stage B: a revoked but unexpired access token still gets a code, so it is linked while `/api/auth/me` says false (once) | The exact `getValidAccessToken` for issuing narrows it. The revoked-token branch deletes the tokens, so the next whoami has no proof. Covered by the Stage B test. |
| Stage C: a returning chat-signed-in customer whose token died keeps a dead `customer_account` link, and the widget wipes local history once | Phase 2 repair (`downgradeCustomerAccountLink` on redeem). Residual: on a transient DB error, a live Customer-Account link of the same customer is downgraded and order status asks for one more chat sign-in. |
| A tab open longer than the max age loses the shop proof: the next account call 401 → the widget wipes local history and rotates the sid without a KPI event (04 §8, 05 §3.3) | 24 h default; every new tab renews. History stays server-side. Documented in 02 §7.3 / 05 §3.3. |
| Shop logout within the same tab is not noticed (04 §5.6) | Bounded by the max age. Whether a shop logout revokes the Customer-Account token is **unverified** (§2); verified in Stage A. |
| After the chat's local „Abmelden“, a new tab re-links through the shop (04 §5.6) | Expected shop-login behaviour. Documented. |
| Consent ask repeats for shop-recognised customers (per-tab dismiss, per-device decline) | Backend anti-nag (§4) before Stage C, plus the per-customer check in §8. |
| Consent popup bullets and `/en` copy reach a larger audience in Stage C | D-AP4 and D-AP3 are Stage C preconditions. |
| Event inflation: one recognition per tab session | All KPIs count distinct sessions, never events. |
| The manual whoami check writes real rows (a recognition, and in Stage B/C an unredeemed code for a fake sid) | `session=livecheck-manual`. Every new KPI query and `verify:live` section 7 exclude `livecheck-%`. The automated `verify:widget` call has no shop cookie and writes none. |
| Handover can be triggered for a known sid by a crafted whoami link | It only **ends** a link (no data access), and knowing someone's sid is already required. Acceptable. |
